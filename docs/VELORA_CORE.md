# Velora Core: implementation and rollout

Velora SMP targets Minecraft 1.20.1 and Fabric. The display names are **Velora Core (Server)** and **Velora Core (Client)**. This is a partial implementation, not completion of the seven-module specification. Retired experiences remain in source and storage. No production instance, deployment, player balance or local runtime store was changed by this source work.

## Product decisions

- Starting balance: $1,000 for a new economy account; currency: dollars.
- Casino wagers use existing in-game balances. There is no real-money purchase, payout or payment integration.
- Virtual market settlements default to a 10% fee, rounded to the nearest cent with halves upward. Auctions pay the seller the highest bid. Pedestal physical shops charge no virtual fee; their linked stock chest opens protected server storage.
- New factions cost $750, start with 16 claim capacity and permit eight members. These defaults are editable in the experience editor.
- New, unconfigured SMP vault settings offer 54 total pages, with one free seven-row by nine-column vault. Additional pages require purchase. Existing configured inventories are retained.
- Unpaid faction upkeep gets a three-day (72-hour) grace period from the oldest unpaid bill, then freezes new claims; existing claims are retained. Chunk/member rates, grace days and rivalry cooldown are editable in the experience editor.
- Buy-contract acceptance deadlines are chosen by the requester per contract.
- Rivalry rewards must reject repeated kills of the same player within an admin-configurable cooldown.
- Burst uses a risk ladder: advance a round or cash out. Multiplayer casino rooms, leaderboards/tournaments and custom casino blocks are explicitly deferred.

## Experience selection and compatibility

The admin experience editor offers the Velora SMP template and an explicit **Activate Velora SMP only** action. Activation requires a Fabric 1.20.1 instance. It transactionally disables other instance records and enables the selected one, while preserving their IDs, settings and data. Disabled instances reject player/game-server scoped requests; administrators can still inspect and manage them. Creating a new Fabric 1.20.1 instance uses the SMP template. This does not automatically activate it as the sole experience or stop existing Minecraft processes.

The instance experience owns a versioned `modules.velora_core` policy. The host derives feature visibility from it; legacy quests, achievements, collections, content, events and companion layout pages are absent from the SMP preset. The companion request bridge remains available as transport for allowed Core operations, including maps. Backend capability checks remain authoritative.

Existing protocol channels (`scopenet:s2c`, `scopenet:c2s`), Fabric mod identities (`scopenet`, `scopenet_client`), config filenames, database paths, vault files, credential stores and updater identities are preserved. Internal `guilds` IDs and API paths remain compatibility identifiers; the SMP navigation calls them Factions. Legacy loader implementations and presets remain available in source. Reusable platform contracts do not embed Velora gameplay policy.

## Casino rules and recovery

Roulette has 37 equally likely pockets (0–36). A single number returns 36 times the stake; red/black, odd/even and low/high return twice the stake; dozens return three times the stake. Zero loses outside bets. These returns include the stake, have a base expected return of 36/37, and are subject to the admin payout cap. Roulette does not use Chaos.

Burst defaults to 12 steps, 72% survival per step and a 4% base house edge. At step zero the player may recover the stake. After surviving `n` steps the uncapped cash-out is `stake × (1 − house_edge) / survival^n`, rounded to cents and capped by the snapshotted payout limit. Failure loses the stake; the final successful step automatically pays. Odds, edge, length and payout cap are saved with the round, so later admin changes do not rewrite an existing wager. Closing the individual game prevents advancing while allowing cash-out. Disabling the whole module still blocks its routes: operators must settle active stakes before retiring it.

Burst start, advance and cash-out and Roulette spins require operation UUIDs scoped to the authenticated player, server and action. Retries return the stored receipt. Burst actions also require the round ID and expected step count; stale actions and another player's round are rejected. The shared interfaces retain the same operation UUID when retrying. Active Burst rounds resume after leaving the page. The casino scheduler automatically cashes out Burst rounds older than `casino_abandon_hours` (24 hours by default), measured from stake creation. It uses the earned, snapshotted payout, records a receipt and history entry, and does not pay twice on retry.

## Contracts, upkeep and rivalry rules

SMP buy contracts require a requester-selected duration of 5 minutes–30 days, starting on acceptance. Reaccepting cannot extend it. The accepted player must hand in the plain items before the deadline. Expiry or abandoning an accepted SMP contract closes it and refunds escrow once; legacy reservations still reopen. Unaccepted listings use the existing listing expiry. `/orders request <amount> <total dollars> <item> <deadline minutes>` posts from game; the launcher/web form exposes the same deadline.

Upkeep records one immutable bill per faction and UTC date, using the chunk/member counts at billing: default `$2 × chunks + $1 × members`. All recorded unpaid bills are paid oldest first from the faction bank, without a negative balance or partial bill payment. The scheduler checks each minute. An unpaid bill freezes new claims after 72 hours; deposits settle arrears and restore new claims on the next scheduler run. Existing claims are never deleted. Rates and grace duration are configurable. Missed days while the panel is entirely stopped are not reconstructed or charged retroactively.

Faction leaders propose and accept rivalry terms: fixed dollars or a percentage of the victim's balance, with an optional duration of 1–8760 hours or permanence. Acceptance checks the exact terms revision and applies both directions in one transaction. Rewards debit the victim and credit the killer within the game sync transaction, capped at the available victim balance. The default cooldown is 60 minutes, configurable per experience, shared across killers in the same faction for the same victim. Game sync receipts suppress replayed batches. Fabric relays player-caused deaths; live Minecraft/mixin/auth acceptance remains required. Accepted alliance grants currently mirror the same permissions in both directions; separate grants and a complete player editor remain unfinished. Faction upgrades and vaults have source implementations; outpost purchases now deliver an identified vanilla banner through the cloud mailbox. Holding it and running `/faction outpost place` registers an immutable anchor and consumes the banner after confirmation. Claim the anchor chunk first, then adjacent chunks; each area allows twelve chunks within three chunks of the anchor, sharing total faction claim capacity and upkeep. Placement must avoid claimed land and overlapping outpost areas. A placement retry at the same coordinates is idempotent. Existing disconnected claims remain intact. Previously paid provisional outpost upgrades require operator reconciliation before rollout; no existing tiers are silently reset.

## Darknet catalog and delivery

The admin editor loads/saves a catalog of at most 200 products through the scoped `/api/admin/economy/darknet` endpoint. Each product uses `id`, registered namespaced `item_id`, `item_name`, `amount` (1–64), positive integer `price_cents`, and `enabled`. Arbitrary command execution and custom NBT are not catalog features.

Player routes are `/api/v1/board/{server_id}/darknet` and `/darknet/buy`. Player identity comes from authentication, not a submitted UUID. Purchases carry an operation UUID; retries return the original receipt and cannot buy a different product with that identity. The UI sends its reviewed price so a price change requires a fresh review. A single database transaction debits currency, records the ledger/receipt and inserts the vault delivery. Game-server routes use the existing authenticated server credential. Both economy and vaults must be enabled for Core purchases.

Fabric 1.20.1 now stores vault contents in the panel. A game server leases a vault while open, saves revisions and releases it on close. Saves from the Core integration carry operation UUIDs and exact-request receipts; a lost response retries the same snapshot before later edits are sent. Reusing a save identity with different contents is rejected. Legacy callers can omit the optional operation UUID and retain revision-only behavior; launcher/web moves require both vaults to be unlocked and unleased. Delivery IDs are removed in the same transaction as the cloud write. Local files are imported once and retained as migration backups; an active lease or existing cloud contents prevents import overwrite. Exact serialized item data stays on the server. Prepared custody and the player-data checkpoint now coordinate vault inventory changes across the two stores. Live restart/crash/lost-response acceptance remains required before production use.

## Map provenance

The requested reference is [pacificminer/map](https://github.com/pacificminer/map), an older Paper-oriented Pl3xMap implementation. No upstream source was copied in this change. The current renderer remains Velora's existing region-file map producer. The 1.20.1 client tile cache adapts existing repository client code, bounds downloads/cache sizes, rejects redirects and requests tiles with short-lived map tokens. A future upstream port must preserve its license and dependency attributions; MIT does not cover every repository file or Velora artwork/trademarks.

## Authentication and rollout gates

### Continuation after the cloud-vault/faction backend work

The cloud-vault, upgrade and accepted-alliance source additions were present when this continuation started; their launcher/web integration and documentation were unfinished. The continuation adds shared vault and faction-market screens, authenticated native commands, reviewed upgrade prices, locked-vault edit checks, import lease/duplicate guards, and a player-facing faction-vault role permission. Leaders/officers can use faction storage; ordinary members cannot. New custom roles default to no storage access; assigning a role with `can_vault` grants it. Previously persisted role grants are retained and should be reviewed before rollout.

Personal vault unlock prices and faction upgrade prices/limits are editable in the experience editor. The Utilities editor controls total available personal vault count and free count. New unconfigured Core instances offer one free page and up to 53 paid pages; the player list shows owned pages and the next unlock. Darknet offers the next permanent vault unlock using the same reviewed price and purchase receipt as the Vaults screen. The `velora-vault-` product prefix is reserved for these entitlements.

Player cloud routes are `GET /api/v1/vaults/{server_id}`, `POST .../move` and `POST .../buy`. Moves send source/destination owner keys, vault numbers, slots and reviewed revisions; users cannot submit or alter item serialization. Purchases send number, reviewed price in cents and an operation UUID. Native commands `vault_get` and `vault_post` use the existing authenticated account/experience context, and accept only `move` or `buy`. Game routes are `vault/open`, `vault/save`, `vault/renew`, `vault/import`, `vault/buy` and `vault/entitlements` under the existing authenticated server API. Faction upgrades use `GET/POST /api/v1/guilds/{id}/upgrades`; new screens submit both the reviewed tier and price. A replayed tier cannot buy twice, and a changed reviewed price is refused. Existing in-game callers that omit the optional reviewed price retain their protocol shape.

`casino_abandon_hours` and `analytics_retention_days` now control Burst settlement and raw-event retention. `shop_requires_claim` and `shop_promotion_cents_per_day` now control pedestal construction/purchases and map promotion; both are exposed in the experience editor. Remaining work includes the requested upstream map renderer, expanded native listing/contract and faction management forms, analytics dashboards and live custom-auth/recovery/permissions acceptance. Casino rooms and custom blocks remain deferred.

Keep the existing custom Yggdrasil/authlib-injector setup and `online-mode=true` requirement. Keep server credentials out of client config and packets. The native map bridge sends only the panel base URL and scoped temporary tile token. Client display switches never substitute for server authorization.

Before manual rollout:

1. Back up the instance database and Minecraft worlds/config/vault storage using existing operational procedures. Retain all SQL migrations.
2. Build the two 1.20.1 jars and install each on its intended side; seven-row vaults require the Core client. Test with synthetic accounts and the custom authentication service.
3. Verify login/session revocation, module deny behavior, market fee conservation/retries, faction charge rollback, and offline Darknet delivery across restart/full vault/acknowledgment failure.
4. Exercise map uploads/tokens and dimension changes, fullscreen/minimap scaling, claims/warps/player filters and memory/frame performance.
5. Finish missing gameplay above before advertising the full specification. Validate upkeep/grace timing, contract expiry/refund and rivalry transfer/replay with synthetic game clients. Casino rooms and blocks are deferred; define event limits and stage-load-test them when that work resumes.
6. Activate the selected SMP instance in the admin editor only when ready for cutover. Stop/reconfigure old server processes separately. Packaging and release remain manual; no paid infrastructure is introduced.

Operator setup (token, config file, sign-in flag) is in [the setup guide](VELORA_CORE_SETUP.md). Build commands and acceptance limitations are in [the integration guide](https://github.com/VeloraMCDev/velora-launcher/blob/main/integrations/velora-core/README.md). This document records source behavior, not a successful production deployment.

## Inventory custody, pedestal shops and native controls

Vault clicks transfer a whole stack with no carried cursor stack. The panel prepares the exact before/after vault state and pins its lease. Fabric locks inventory-affecting packets and pickup/damage/death, checks the original inventory, writes the changed inventory and transfer UUID to the player's existing UUID.dat using a forced temporary file and atomic replacement, then asks the panel to commit. Lost responses retry the same transfer. On reconnect, a matching loaded checkpoint commits; an absent checkpoint cancels. Unresolved custody blocks game opens, saves, imports and launcher/web editing independently of lease expiry. Recovery finish/pending routes remain usable with the vault module disabled. A panel outage keeps inventory locked and reports that reconnect recovery is needed.

This protocol covers Fabric cloud-vault and shop-stock clicks. It does not turn arbitrary third-party inventory writes or the existing market-listing/contract hand-in journals into the same protocol. Filesystems must support atomic replacement; ambiguous write failures disconnect the player for recovery. Corrupt player files, selective backup restoration and disk/power failure require reconciliation of both stores. SQLite uses FULL synchronous writes. These properties need verification on the staging server's filesystem and actual modpack.

The physical shop is a polished blackstone slab with an ItemDisplay product, linked to an empty vanilla single chest within two Manhattan blocks. The chest is a portal to a three-row cloud stock inventory; it does not hold a second vanilla copy of stock. Setup samples the held item without consuming it. Stock restocking/withdrawal uses the vault custody protocol. Purchases consume the exact registered item/tag fingerprint, debit the buyer, credit 100% to the seller and queue an exact-NBT vault delivery in one receipt transaction. Sales wait while stock is open or prepared. Claim ownership is checked again at purchase when the admin requires claims. Breaking shop blocks leaves stored stock recoverable. Vanilla hoppers are excluded from registered stock chests; other automation mods need staging compatibility checks.

Commands: hold the product, look at the slab, then /pshop create <dollars> [quantity]. Right-click the chest to restock and close it before sales. Right-click the pedestal for the native purchase review, or use /pshop buy after the chat quote. /pshop stock <shop UUID> recovers owned stock even when blocks are missing. /pshop price <shop UUID> <dollars>, /pshop close <shop UUID> and /pshop reopen <shop UUID> manage a shop. /pshop promote <shop UUID> <1-30 days> [warp] reviews the current listing fee; append confirm to buy. Defaults are $50/day, configurable in the experience editor. Promoted pins appear through the existing filtered player map feed. /pshop visit <shop UUID> uses an active opted-in warp and a safe destination. A shop ID is returned during setup; shop construction does not create a new custom block registry identity.

K opens the expanded native hub: Market, Darknet, Casino, Faction, Map and Vault 1. V opens Vault 1; M opens the map. Native casino rounds are server-authoritative, require wager confirmation, and resume active state from the lobby. Failed/uncertain mutations require refresh before another wager; no automatic financial retry is sent. Native Darknet retries retain the purchase operation UUID. The faction screen shows roster/bank information, validates bank amounts and delegates actions to existing permission-checked faction commands. Advanced management and listing/contract forms remain available through commands and the launcher/web panels.

Permissions management requires the Fabric LuckPerms mod alongside Core. The existing panel Permissions and Chat editors remain the control surface. Explicit panel commands operate regardless of the optional automatic mapping flag; automatic panel rank/group mapping is off unless integrations.luckperms.apply-panel-groups=true. Existing LuckPerms identities/nodes are retained. Core chat preserves the original signed message, formats unsigned presentation through a custom content-only chat type, and leaves filtered or nonstandard chat types alone. Test moderation and other chat mods before rollout.
