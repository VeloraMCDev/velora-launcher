## Initial findings and patch gates

1. **Ownership/admission blocker in current code:** `commands::cancel_launch` takes any task regardless of instance and immediately emits idle. `start_task` admits a replacement when the abort handle reports finished, not when an owner monitor publishes completion. Replace with the actual manager, not fixture-only evidence. Cancellation must match the active instance, ignore a finished worker, be idempotent and retain the slot until its JoinHandle resolves. Completion must check the exact internal UUID before publishing and clearing; a stale completion must never clear or emit terminal state for a replacement.
2. **Mutation TOCTOU blocker in current code:** delete/cache mutation has no preparation exclusion; username checks game/task and then awaits HTTP without reserving admission. All scoped entry points must acquire the same global mutation lease before inspecting the registry/game list. Start must use nonwaiting `try_lock_owned`, then reserve the manager slot and move the lease into the worker. Rename must retain its lease through response parsing, credential/account persistence and error paths. Delete/cache must retain theirs through filesystem completion. A busy lease must produce the existing result shape, not change IPC arguments or return types.
3. **Lock discipline:** no synchronous preparation/game/settings/accounts guard may cross an await. Admission should acquire lease, then briefly manager/game guards in a consistent order; no path may await lease acquisition while holding those guards. Monitor awaits the worker without managerlock, validates owner UUID under a short lock, publishes lock-free while retaining the occupied slot, then clears the exact finished owner under a new lock. Audit callback telemetry capture: it synchronously reads settings/accounts and credential storage; never call it while retaining a game/settings/accounts lock that it can reacquire. Keep network telemetry detached from managerlock.
4. **Success/error/cancel semantics:** successful launch already publishes running; the preparation monitor must not overwrite that with idle. Repair already publishes its completion inside `game::run`. Decide worker error versus abort versus panic from the actual JoinHandle result; a late cancel after task completion must not relabel success. Inspect whether lease is released before terminal publication: registry exclusion must still reject preparation during that gap. Mutation entry points may safely proceed only under the explicitly limited Rust-future guarantee, not a claim of all-resource quiescence.

## Explicit remaining gates (not silently fixed by this batch)

- **Abort is not filesystem quiescence.** Core HTTP/sync use awaited filesystem operations; aborting an awaiting future and joining it does not establish that previously dispatched blocking filesystem work has stopped. Old writes/removes may outlive the mutation lease. No direct manager test proves otherwise. Native/isolated filesystem acceptance and a cooperative drain/ownership strategy remain gates before claiming safe rapid destructive mutation after cancellation.
- **Process handoff:** `game::run` spawns Java, then the close-after branch awaits 1.5 seconds and exits without ordinary run registration. Core `launch::spawn` does not set kill-on-drop. Cancellation there can leave Java alive/unregistered. The ordinary branch has no await between spawn and registration; do not misdescribe it as the same race. Detached readers/watcher outlive preparation by design. A blanket kill-on-drop would break intentional game survival on launcher close and is not authorized.
- **Running-game compatibility:** deep repair checks the matching running instance; delete must check it too; username must reject every running game. Ordinary launch remains multi-window capable, and installer work still precedes `already_running` in `game::run`. This narrow lease is not a complete running-game write barrier. Verify native close/hide/minimize, spawn failure, handoff and game survival separately.
- **Public identity limitations:** cancel IPC carries only instance identity, so a delayed same-instance cancel can target a newer preparation. Progress/logs lack operation/run attribution. Old watcher removes only its run UUID but emits unconditional instance idle; frontend accepts idle without owner filtering. These remain documented, not solved by internal preparation UUIDs.
- **Telemetry identity:** `game::run` captures a recorder at start, but watcher exit and current command error paths call state-based telemetry capture again. Switching accounts can therefore change attribution. Scoped lease protects rename, not all account-selection/settings/manifest mutations; do not claim a fully immutable launch/account snapshot.
