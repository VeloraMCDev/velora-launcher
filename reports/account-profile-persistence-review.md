## Resolved P1 and bytes-helper refinement

The original P1 used predictable `secrets.bin.tmp` with symlink-following `std::fs::write`, allowing unrelated target truncation before account JSON validation. Current `Secrets::flush` no longer references that path: it delegates encrypted bytes to `persistence::atomic_write_bytes` and validates any existing ciphertext by decrypting and decoding it with the same already-loaded key. Invalid/wrong-key ciphertext and ordinary symlink/nonregular destinations fail closed, both before creating a temporary and before rename. Persistent names, encryption format, keyring identity and fallback-key behavior are not changed by this refinement. `Secrets::open` can still read through a symlink; this is not a write-safety endorsement of symlinked stores.

The shared bytes writer uses a UUID sibling, exclusive `create_new`, private Unix creation mode, regular-file checks, write-all/file-sync/close, and Unix device/inode revalidation before destination revalidation and rename. Pre-existing collision paths are not truncated or removed because failed exclusive open returns before cleanup. After an owned temporary is created, failure attempts removal and preserves the primary error; cleanup failure is logged. Identity checks are not handle-bound cleanup/publication under malicious concurrent path replacement, which remains the explicitly narrow TOCTOU gate below.

`write_json_with` now serializes and delegates to the same writer with a `read_json::<Value>` validation closure, preserving pre-publication and pre-rename JSON validation, injectable write/rename callbacks, sibling checks, exclusive creation and cleanup semantics. The existing ten JSON helper fixtures remain present, including partial writes, failed rename, collisions, corrupt-during-write, unsafe temporary locations, symlinks/nonregular files, private permissions and cleanup failures. Serialization now precedes initial destination validation; this can change which error is returned for simultaneous serialization/input faults but cannot mutate the destination before validation. No source regression found; these fixtures must pass in the final run.

## Accepted source behavior

- `AccountsFile::update` clones, changes, persists, then replaces memory under the AppState write lock. Offline addition and selection use it. Invalid selection fails before persistence. Existing IDs, UUIDs, kind/panel identity matching and active-account fallback ordering remain unchanged.
- `save_panel_account` validates required Yggdrasil data before acquiring the account write lock or mutating either store. It upserts only the candidate and preserves the original ID. Credentials publish before account JSON; memory commits only after both return success.
- Removal clones accounts, removes the ID, chooses the first remaining account only when removing the active account, then uses credential removal with account-save commit. Account and secret in-memory maps remain old on ordinary failures. Login, Discord completion, registration, offline, select/remove and rename handlers route into these helpers. The logout telemetry still precedes persistence and may report a failed removal, but this is unchanged behavior.
- `Secrets::set`/`remove` now clone before flushing. `change_with_commit` serializes credentials under its mutex, attempts account publication, and attempts restoring the old map on account-save failure. It reports rollback failure with the original error context rather than returning success. The accounts-to-secrets lock order matches `panel_token`; no reverse acquisition found in reviewed paths. No inspected account/profile mutex/RwLock guard spans a network await.
- Account/profile JSON calls share `read_json`/`atomic_write_json`: malformed JSON, nonregular destinations and ordinary destination symlinks are rejected before overwrite; UUID-exclusive sibling output is file-synced and closed before rename, with Unix temporary inode checking. Accounts load defaults for display without changing corrupt source bytes, but subsequent save refuses those corrupt bytes. Profiles load errors rather than pretending a corrupt wardrobe is empty.
- All profile read/update handlers take the AppState profile mutex. Save performs HTTP/image resolution before acquiring it, then loads and modifies the latest disk list under the lock. Apply clones the selected profile inside a lexical lock block and releases it before any HTTP await. Missing profiles allow a first save; same-ID replacement and deletion semantics remain intact. Fail-closed profile loading is an intentional error-behavior change, not byte-identical extraction.

## Inspected tests and remaining failure limits

Eleven account fixture tests and three profile fixture tests are now inspected. Existing credential failure coverage now makes the destination a directory rather than obstructing the unused legacy temporary. Three added fixtures cover the legacy temporary symlink remaining untouched with unrelated bytes preserved across saves, encrypted-destination symlink rejection with account/target preservation, and a deterministic failed rollback retaining both failure messages and recoverable credential bytes at a fixture-controlled recovery path. The last fixture deliberately moves the successfully published candidate and replaces its destination with a directory, causing rollback refusal; it checks old in-memory credentials and account identity. It is not evidence of an automatic backup facility or a real account-rename syscall fault. Direct encrypted external-corruption/same-key concurrent-writer fixtures would strengthen coverage; the source validator itself rejects corrupt/wrong-key bytes. All latest fixtures were read, not run by this reviewer.

Inspected `/private/tmp/velora-revitalization-50/host-integration.log`: completed host test profile and 56 passed, zero failed/ignored. This is earlier evidence supplied by the lead, before the latest bytes refinement; final integrated validation is still conditional. HTTP-only Panel/client changes are visible in account/profile files and are not included in this follow-up's compatibility verdict; the persistence functions and profile lock boundaries inspected remain as previously reviewed.

Two independent store renames are not a durable transaction. A crash between credential and account publication can retain new credentials with old account metadata, or remove credentials for an account still on disk. Failed rollback leaves disk at the candidate while memory remains old; the error is surfaced, but there is no durable journal, automatic recovery or poisoned-store latch preventing further mutations. Concurrent processes are not serialized. A local save cannot roll back a username already changed remotely. These limits remain explicit gates rather than native/crash acceptance.

Serde acceptance is not future-schema compatibility: unknown JSON fields can be accepted then dropped on save, and valid future account kinds can be filtered out. No versioned migration/forward-preservation contract is proven. Atomic replacement creates restrictive new files but does not preserve previous ACLs/modes/ownership; no parent-directory fsync proves crash durability. Ancestor symlinks and check-to-use races are not handle-bound containment. Shared typed-client work and responses arriving after account switching need separately scoped review.
